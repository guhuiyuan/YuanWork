## 1. 系统架构

### 1.1 模块划分

| 子系统 | 模块 | 职责（做什么） | 不做什么 | 依赖 |
|--------|------|--------------|----------|------|
| 运行时 | `Paths` | 定下本项目可写状态的落点：数据目录（索引、日志、审计）与模型缓存目录；在进程最早期把模型缓存目录写进 `HF_HOME` | 不按剩余空间自动改道；不碰系统盘上其他程序的东西 | 环境变量、.env |
| 工作域 | `Workspace` | 管理工作域（一个文件夹 + 手动加入的单文件），给出文件清单与变更 | 不做自动文件监听；不做跨工作域检索；不解析文件内容 | 关系库 |
| 解析与索引 | `ParserDispatcher` | 按扩展名从解析器中选出唯一匹配者 | 不做内容嗅探；不校验扩展名是否与真实格式一致 | 解析器 |
| 解析与索引 | `PDFParser` | 提取每页文本与表格，给出页码锚点 | 不做扫描页 OCR；不做多栏分栏 | PyMuPDF（主路径）、pdfplumber（表格与复杂版式兜底） |
| 解析与索引 | `DocxParser` | 按标题分组段落，表格转 Markdown，**读出内嵌图片与文本框里的文字**（扫描件与实验报告模板），给出章节锚点 | 不识别中文标题样式；不描述图片内容 | python-docx |
| 解析与索引 | `PptxParser` | 按幻灯片提取标题、文本、表格与备注，**读出图片里的文字**，给出幻灯片号锚点 | 不提取组合形状内的文本；不提取图表；不描述图片内容 | python-pptx |
| 解析与索引 | `XlsxParser` | 把每个非空工作表转为 Markdown 表格，给出工作表与行号锚点 | 不计算公式；不读取图表 | openpyxl |
| 解析与索引 | `MarkdownTxtParser` | 解析 ATX 标题分节或按空行分段，给出标题路径锚点 | 不识别 Setext 标题；不做编码嗅探 | 标准库 |
| 解析与索引 | `ImageParser` | 用 OCR 识别图片文字，产出逐行块加全文块 | 不描述图片内容；不应用 EXIF 方向 | rapidocr-onnxruntime |
| 解析与索引 | `ocr` | 用同一个 OCR 引擎读出**文档里内嵌图片**的文字，供 docx 与 pptx 解析器调用；引擎按进程加载一次 | 不描述图片内容；不做版面还原 | rapidocr-onnxruntime |
| 解析与索引 | `StructuralChunker` | 把块切为切片并保留块元数据；**切片长度按嵌入模型读得下的 token 量算**（同一个配置，ADR-046） | 不做语义切分；不做短块合并 | 嵌入模型的 tokenizer |
| 解析与索引 | `SlicedEncoder` | 把切片变成向量：批按**设备实测**的预算切（显卡看显存、CPU 看核数），设备吃不下就切半，向量直接留在数组里 | 不算稀疏通道（那是库的活，且检索侧不读）；不替设备决定该读多长 | 嵌入模型 |
| 解析与索引 | `IngestionPipeline` | 串行编排解析、分层、切块、向量写入与元数据落库 | 不做增量更新；不限制文件大小；不编译长尾层文档 | 分发器、切块器、分层判定器、语义记忆 |
| 解析与索引 | `BatchIngestor` | 并行批量摄取：多进程解析（工人数按机器的物理核数定）、批量嵌入、限流与断点续跑 | 不做跨工作域并行；不改变单个文件的摄取语义 | 解析器、语义记忆 |
| 解析与索引 | `TierClassifier` | 判定一份文档属核心层还是长尾层 | 不做内容语义分类模型；不改写用户显式指定的分层 | 配置、模型网关 |
| 检索 | `HybridRetriever` | 编排两路召回、融合与截断 | 不打分；不设置超时 | 语义记忆 |
| 检索 | `TieredRetriever` | 先查核心层页面再查长尾层切片，核心层结论足够时短路 | 不做两层之间的分值融合；不静默丢弃长尾层证据 | 语义记忆、`HybridRetriever` |
| 检索 | `FTSIndex` | 维护倒排索引，提供增删与 BM25 检索；攒着写，攒够了自己刷一次 | 不做向量检索 | tantivy、jieba |
| 检索 | `Reranker` | 用交叉编码器对候选重排 | 不在缺模型时阻塞主链路 | FlagEmbedding |
| 检索 | `ConfidenceScorer` | 由检索结果计算检索侧分数 | 不读取模型自评结果 | 无 |
| 检索 | `EvidenceGate` | 执行双闸拒答判定：硬规则与模型自评 | 不生成答案 | 检索器、置信度打分器、模型网关 |
| 编排 | 模型网关 | 唯一模型出口：路由、参数、流式、审计 | 不做重试与限流；不做提示词清洗 | LiteLLM、审计器 |
| 编排 | `AgentLoop` | 维护状态对象、按序执行各步骤、生成事件流 | 不并行执行步骤；不校验模型语义输出 | 各步骤模块 |
| 编排 | `ConflictJudge` | 用前置规则筛选后独立判定模型答案与知识库是否冲突，并给出以知识库为准的答案 | 不改写引用编号；判定失败时不泄漏模型认知 | 模型网关 |
| 记忆 | `EpisodicRecorder` | 把用户与知识库的交互记为情景事件，并按条数与时间双上限淘汰 | 不采集应用外的工作痕迹；不存对话原文以外的任何用户数据 | 关系库 |
| 记忆 | `ConsolidationEngine` | 从情景事件归纳实体、规律与页面更新，写回语义记忆；规律以待审状态入库 | 不做真实去重合并；不实现冲突归档 | 关系库、模型网关 |
| 记忆 | `SQLiteStore`（实体、关系、编译页面）与 `SemanticMemory`（切片向量与倒排） | 实体、关系、编译页面落关系库；切片向量与全文倒排落向量库与倒排索引 | 不把向量写进关系库 | 关系库、向量库 |
| wiki | `WikiCompileTrigger` | 判定是否编译页面、派生主题与标题、维护冷却 | 不落盘冷却状态 | 关系库 |
| wiki | `WikiPageGenerator` | 把证据簇编译为结构化页面，抽取摘要、要点与出处；按段落归属合并重编译 | 不覆盖用户所有的段落 | 关系库、模型网关 |
| wiki | `WikiEditor`（编辑落库在 `SQLiteStore.update_wiki_page`，段落级归属在 `WikiPageGenerator` 的合并里） | 接收用户对页面的编辑并标记段落归属 | 不改写模型生成的内容；不自行合成正文 | 关系库 |
| wiki | `CoreCompiler` | 在摄入时通读核心层文档原文，编译出实体页、概念页与对比表 | 不编译长尾层文档；不在提问关键路径上编译 | 模型网关、语义记忆 |
| wiki | `WikiLinker` | 建立页面之间与页面到原文之间的链接 | 不从正文猜测链接 | 关系库 |
| wiki | `EntityExtractor` | 抽取实体与关系并写入图谱 | 不写入不在类别白名单内的实体 | 关系库、模型网关 |
| wiki | `WikiGraph` | 构建可浏览的实体与页面图谱 | 不落盘；每次实时构建 | 关系库 |
| 隐私 | `NetworkGuard` | 在套接字层拦截出站连接 | 不放行本机代理的隧道流量；不拦截子进程 | 标准库套接字模块 |
| 隐私 | `AuditLogger` | 记录每次模型调用的元数据 | 不记录提问与回答原文；不做轮转 | 模型网关 |
| 隐私 | `Redactor` | 在片段发往模型前替换敏感字段 | 不修改本地存储 | 标准库正则模块 |
| 对外接口 | 应用工厂与生命周期 | 创建应用、装配路由、初始化与释放组件 | 不回显内部异常原文 | 全部业务模块 |
| 对外接口 | 请求与响应模型 | 声明各端点的入参与出参结构 | 不做业务校验 | 校验库 |
| 对外接口 | 对话路由 | 提供流式问答、阻塞问答与取消 | 不做请求级并发控制 | 编排层 |
| 对外接口 | 工作域路由 | 管理工作域与工作域文件清单 | 不做后台任务队列 | 工作域 |
| 对外接口 | 摄取路由 | 触发索引建立与重建、报告建库进度与**读不进来的文件**（路径 + 原因） | 不做后台任务队列 | 摄取管线 |
| 对外接口 | wiki 与记忆路由 | 页面、反链、图谱、情景事件查询、整合触发 | 不做鉴权 | 关系库 |
| 对外接口 | 审计路由 | 审计查询、统计与清空 | 不做鉴权 | 审计器 |
| 桌面端 | `sidecar` | 定位解释器与后端目录、定端口、拉起后端、探活、退出清理 | 不做后端崩溃检测与自动重启 | 环境变量、目录结构 |

| 桌面端 | 组件层 | 渲染对话、工作域面板（**含知识库文件清单与读不进来的文件**）、wiki 三视图与引导、**右栏的推理轨迹与审计**（ADR-053、ADR-056） | 不做错误边界 | 前端状态 |

### 1.2 数据流向

**建立与重建索引**

```
工作域（文件夹 + 单文件）
  → 枚举受支持文件 → 计算内容哈希 → 内容相同的跳过
  → 解析为块（带位置锚点）→ 结构切块
  → 文档分层：核心层 or 长尾层
      ├ 核心层 → 模型通读原文
      │   → 抽取实体与概念 → 更新/新建实体页、概念页
      │   → 与已有页面比对 → 发现矛盾则生成对比表（保留双版本）
      │   → 每条结论附出处锚点 → 写页面与双向链接 → 更新索引页
      └ 长尾层 → 写入向量索引 + 全文索引
  → 写入文件元数据行
```

**提问一次**

```
提问 + 会话标识
  → 理解步骤（模型调用：意图、主题、文件线索、时间线索）
  → 定位步骤（文件名匹配 + 向量召回 → 候选文件）
  → 抽取步骤（先查核心层页面 → 核心层结论不足时才查长尾层切片 → 证据集 + 检索侧分数）
              （两层都无可用证据 → 拒答）
  → 证据闸（硬规则：证据条数、每条证据可定位
              模型自评：这些证据能否回答这个问题
              任一不过 → 拒答分支）
      ├ 拒答 → 最可能位置 + 改进建议 → 记情景事件（类型=提问）→ 返回
      └ 通过 → 回答步骤（模型调用，基于证据生成带引用的答案）
                （核心层页面与长尾层切片结论不一致 → 以核心层页面为准并标注不一致）
                → 引用校验（解析答案里的引用编号；越界或缺失 → 转拒答）
                → 冲突判定（独立模型调用）
                    ├ 冲突 → 以知识库内容为准的答案 + 开头显式标注分歧
                    │        → 写冲突记录 → 记情景事件 → 返回
                    └ 无冲突 → 原答案 → 记情景事件 → 返回
```

**整合一次**

```
情景事件（近 N 轮）
  → 归纳：候选实体、候选规律、页面要点更新
  → 写入语义记忆（实体、关系、页面）
  → 页面自动编译（若有证据簇达到阈值）
```

## 2. 技术选型 ADR

### ADR-001: 按扩展名分发解析器，不用内容嗅探

- **状态**: 已采纳（沿用）
- **背景**: 需要把任意本地文件路由到对应解析器，分发结果直接决定后续是否报错
- **选项**:
  - A. 扩展名匹配 —— 纯字符串判断，零额外 IO；代价是扩展名与真实格式不符时错误延后到解析阶段才暴露
  - B. 读文件头做内容嗅探 —— 能识别伪装格式；代价是每个文件多一次打开，且旧版二进制格式的魔数判定复杂
- **决策**: 选 A
- **理由**: 实现成本接近零，失败会以明确状态暴露在摄取结果里；伪装格式是少数场景

### ADR-002: 内容哈希做去重，内容派生标识

- **状态**: 已采纳（沿用）
- **背景**: 需要判断文件是否已入库，并让切片在多个索引间保持同一标识
- **选项**:
  - A. 内容 SHA-256 加内容派生的标识 —— 改名不换标识、重复摄取幂等；代价是每次要完整读文件
  - B. 路径加修改时间 —— 判定便宜；代价是改名或复制即被视为新文件
- **决策**: 选 A
- **理由**: 工作资料常被复制到多处，内容去重避免同一份合同产生多个文档标识

### ADR-003: 位置锚点用可扩展结构，而不是固定三个字段

- **状态**: 提议
- **背景**: 目标要求 PDF 给出页码、PPT 给出幻灯片号、Word 给出章节、Excel 给出工作表与行号
- **选项**:
  - A. 固定的页码、幻灯片号、章节三个列 —— 实现简单；代价是表格的工作表名与行号无处安放，Word 也拿不到多级标题路径
  - B. 一个锚点结构，含类型与坐标，按类型填充 —— 覆盖 5 类锚点；代价是行结构多一列，引用处要按类型解读
- **决策**: 选 B
- **理由**: 「定位到原文」是产品的核心承诺，Excel 只给文件名等于没兑现；代价可控

### ADR-004: 切块以字符数为单位

- **状态**: 已采纳（沿用）
- **背景**: 切块发生在嵌入之前，需要一个不引入分词器的切分尺度
- **选项**:
  - A. 固定字符上限 —— 实现轻量；代价是中文场景下令牌数波动大
  - B. 按令牌数切分 —— 与嵌入模型对齐；代价是切块链路多一次重量级加载
- **决策**: 选 A，上限 2000 字符、重叠 100 字符
- **理由**: 切块路径保持轻量

### ADR-005: 不丢弃过短的切片

- **状态**: 提议
- **背景**: 现状按最小 50 字符过滤切片，导致块主体为空白时内容被静默丢弃
- **选项**:
  - A. 保留现状的最小长度过滤 —— 索引里没有噪声；代价是原文内容静默丢失
  - B. 不过滤，把短切片并入相邻切片 —— 内容不丢；代价是需要一段合并逻辑
- **决策**: 选 B
- **理由**: 知识库的产品承诺是「引用得到原文」，静默丢内容会让引用与原文对不上

### ADR-006: 两路召回后融合，权重可配置

- **状态**: 已采纳（沿用并调整）
- **背景**: 纯向量检索对纯数字与短中文词召回极差，纯关键词检索无法处理同义表达
- **选项**:
  - A. 两路召回后融合 —— 互补性强；代价是要维护两套索引与两套分词
  - B. 只用向量检索 —— 实现简单；代价是数字与专有名词几乎召不回
- **决策**: 选 A，权重改为配置项而非硬编码常量
- **理由**: 现状的权重是硬编码常量，且被标定在稠密相似度区间上，与融合分的实际区间错配；改成配置项后可随语料重新标定

### ADR-007: 用 tantivy 加 jieba 承担全文通道

- **状态**: 已采纳（沿用）
- **背景**: 嵌入模型自带的稀疏权重对纯数字与短中文词给出的分值为 0
- **选项**:
  - A. 用嵌入模型的稀疏权重 —— 少一个依赖；代价是数字与短中文词完全召不回
  - B. 引入倒排索引加分词 —— 数字与短中文词精确匹配；代价是多两个依赖与一套索引同步
- **决策**: 选 B
- **理由**: 数字类查询是高频诉求，实测嵌入模型稀疏通道对纯数字给 0 分

### ADR-008: 双闸拒答，硬规则与模型自评取更保守的一侧

- **状态**: 提议
- **背景**: 「不知道就说不知道」是产品的核心承诺之一，需要一个可解释、可回归的判定
- **选项**:
  - A. 纯规则（证据条数加分数阈值） —— 完全可预测；代价是拿不住「证据看似相关但不足以回答」
  - B. 纯模型自评 —— 语义理解最强；代价是模型自我评价不可靠
  - C. 两者都要过，取更保守的一侧 —— 覆盖两类失效；代价是多一次调用与一套阈值治理
- **决策**: 选 C
- **理由**: 规则挡住结构性不足（证据太少、定位不到），自评挡住语义性不足；任一不过即拒答，判定可解释、可回归

### ADR-009: 回答步骤做引用校验

- **状态**: 提议
- **背景**: 现状把全部检索到的证据都列为引用，模型实际引用了哪几条无从得知
- **选项**:
  - A. 沿用现状（引用列表等于全部证据） —— 实现简单；代价是用户看到的引用与答案里的编号对不上
  - B. 解析答案里的引用编号，剔除未被引用的证据；出现越界编号即转拒答 —— 引用与答案一一对应；代价是模型改写措辞时解析可能失手
- **决策**: 选 B
- **理由**: 现状的引用列表会把「模型没引用过的证据」也标成引用，用户核验时会发现引用与结论无关，这直接损伤「可核验」这条承诺；解析失败时按转拒答处理，宁可拒答不可给错引用
- **补一句（TASK-087）**: 越界即拒答这条规矩**会把模型的一次编号失误变成用户的拒答**——
  实测模型在答案末尾的「引用来源」一节里**自己重新编号**，编出一个证据里没有的编号（[25]，而证据只有 20 条），
  于是一个本来答得出来的问题以「引用和找到的资料对不上」收场。
  **修法不是放松校验**（放松了就等于给了假引用），而是**把编号范围告诉模型**：
  提示词里写明「只能引用 1 到 N」「『引用来源』一节照抄编号，不要自己重新编号」。
  实测同一问题连跑 6 次全部正常作答（修之前 2 次里错 1 次）

### ADR-017: 引用可打开原文并定位到锚点

- **状态**: 提议
- **背景**: 「能定位」这条承诺要落到可操作，现状引用只展示文件名与页码
- **选项**:
  - A. 只在界面上显示文件名与页码 —— 实现简单；代价是用户还得自己去翻
  - B. 点击引用调用系统默认程序打开该文件并定位到锚点 —— 兑现承诺；代价是需要按格式分别处理定位方式
- **决策**: 选 B（2026-11-20 补充：打开一律用**系统默认程序**，不绑定 Edge——
  别人的设备上未必有；**默认程序定位不到时，应用把位置说出来**，见 AC-F-006）
- **理由**: 这是产品承诺与用户价值的直接连接点。**但「打开」与「定位」不是一回事**：
  PDF 阅读器收到 `#page=N` 这类片段时，Windows 当成**文件名的一部分**
  （「找不到文件 D:\….pdf#page=5」），引用就此死掉；而 `file://` 形式更糟——
  有些阅读器（WPS）会当成别的东西、**打开错误的文件**。真机实测：**默认程序
  （WPS）根本不支持跳页**，所以「打开」交给默认程序，「定位」由应用用话说出来。
  Office 走它自己的自动化（能直接落到幻灯片与工作表）

### ADR-020: 网络守卫收紧本机代理隧道

- **状态**: 提议
- **背景**: 现状放行本机地址，因此指向本机代理的流量可绕过白名单
- **选项**:
  - A. 沿用现状 —— 本地模型可用；代价是本机代理能把全部外网流量隧道出去
  - B. 放行本机地址，但拦截显式配置为代理的连接 —— 堵住隧道；代价是需要识别代理环境变量
- **决策**: 选 B
- **理由**: 现状的绕过面直接削弱了「出站仅限白名单」这条承诺
- **补充（2026-11-18）**: 守卫钩到的是**两个不同的东西**：`socket.create_connection` 看到**域名**，
  而它内部解析 DNS 之后调的 `sock.connect(sa)` 看到的是**解析后的 IP**。白名单里是域名 →
  第二道钩子一个都不匹配 → **允许的域名也连不上**（默认配置下桌面端因此发不出任何模型请求）。
  修法：**钩子看到 IP 时，这个 IP 是否是某个允许域名当前解析出来的地址**——是就放行
  （域名仍然先过白名单）。**留下的漏洞**：共享 CDN 的 IP 上别的租户也能连——
  与「守卫只看得见套接字目标」这个固有限制同类，记在这里备查

### ADR-031: 文档分两层，核心层写入时编译、长尾层查询时检索

- **状态**: 提议
- **背景**: 工作域里的资料有两类性质：合同、规章、法条、内部规范这类需要跨文档关联、结论稳定的核心资料，和零散、频繁更新的日常资料。核心资料要的是「跨文档的稳定结论 + 页码级可回溯」，长尾资料要的是「零散内容的时效性」
- **选项**:
  - A. 全部走长尾路径（切片加检索）—— 单一路径，实现简单；代价是核心资料要靠多次检索拼出跨文档结论，页码引用无从谈起
  - B. 全部走核心路径（写入时编译）—— 结论稳定可引用；代价是每次文件变更都要重编译，零散资料的时效性反而变差
  - C. 分两层，按文档性质分别处理 —— 各自用合适的机制；代价是系统里同时存在两套索引与两条检索路径
- **决策**: 选 C
- **理由**: 两类资料的目标根本不同，用一套机制服务两者，必然在另一类上失分；代价由「分层判定可由用户显式覆盖」兜底

### ADR-032: 编译页面的每条结论都带出处锚点

- **状态**: 提议
- **背景**: 页面上的结论由模型归纳而来，若不带出处，用户无从核验，「能定位」这条承诺在页面形态上就断了
- **选项**:
  - A. 页面只存结论文本 —— 页面读起来干净；代价是结论无法回溯到原文，与模型凭空生成的说法无从区分
  - B. 每条结论都记录原文出处锚点（文件与页码）—— 结论可核验；代价是编译时要多一道锚点对齐与校验
- **决策**: 选 B
- **理由**: 「能定位」是产品的核心承诺之一，页面上的结论同样要能被核验；锚点缺失的结论不进入作答证据

### ADR-033: 摄入时发现矛盾则标记并保留双版本

- **状态**: 提议
- **背景**: 核心层文档被修订后，新内容可能与已有页面的结论矛盾。静默覆盖会让旧结论无迹可寻，用户也无从判断哪个是现行版
- **选项**:
  - A. 静默覆盖旧结论 —— 页面始终只有一份结论；代价是用户发现不了政策已经变了
  - B. 标记矛盾并生成对比表，两个版本都保留 —— 用户看得见分歧；代价是要多一种页面类型与人工裁决入口
- **决策**: 选 B
- **理由**: 合同与规章场景里「用旧条款回答」和「用新条款回答」的代价差别很大；把分歧摆出来由人裁决，比系统替人决定可靠

### ADR-034: 核心层结论足够时短路长尾层检索

- **状态**: 提议
- **背景**: 提问时若核心层页面已给出可用结论，仍去检索长尾切片会拖慢响应，也可能引入与核心结论冲突的低价值证据
- **选项**:
  - A. 两层都检索并融合 —— 召回更全；代价是延迟叠加，且长尾噪声可能稀释核心结论
  - B. 核心层结论足够时不再检索长尾层 —— 快且稳；代价是长尾层的补充信息可能漏掉
- **决策**: 选 B
- **理由**: 核心层承载跨文档关联后的稳定结论，是首选依据；只有它答不上来时长尾切片才是补充，此时才付检索延迟

### ADR-035: 嵌入走 GPU，fp16 且单条截断到 512 token

- **状态**: 提议（**已落地**——2026-11-16 实测装上了 CUDA 版 torch）
- **背景**: 建库耗时的最大单块是嵌入。bge-m3 是 5.6 亿参数模型，在 CPU 上按现有配置（CPU 版 torch、batch 8、逐文件串行）实测估算只有几百 token 每秒，20 GB 规模的嵌入光这一段就要几十小时
- **选项**:
  - A. 维持 CPU 嵌入 —— 零改动，任何机器都能跑；代价是建库时间比目标高一个数量级
  - B. 换 CUDA 版 torch，fp16 推理，批量提交 —— 吞吐提升一个数量级以上；代价是要求机器有 NVIDIA 显卡，且依赖包按 CUDA 版本分发
  - C. 把嵌入外包给云端 API —— 本机零负担；代价是文档内容出本机，与「数据全本地」冲突
- **决策**: 选 B，同时把单条嵌入输入截断到 512 token
- **理由**: 嵌入是唯一能靠硬件直接换时间的环节，而它当前占建库耗时的绝大部分；截断到 512 token 是检索场景的常规做法（bge-m3 官方对检索任务的推荐值），代价是长切片尾部不参与嵌入，但切片本身仍完整入库并可被全文检索命中
- **落地时补的一件事（2026-11-16）**：**Windows 的 PyPI 版 torch 就是 CPU 版**，而官方 PyTorch CDN 在这个网络下只有 0.07 MB/s（2.7 GB 的 wheel 要 621 分钟）——曾经据此以为「CUDA 装不上」。实际上**上海交大镜像**带着 CUDA 索引（`https://mirror.sjtu.edu.cn/pytorch-wheels/cu130/torch/`），`torch 2.14.1+cu130` 实测 11 MB/s，2.9 分钟装完。装上后实测：同一批真实切片，嵌入从 CPU 的 **1.09 切片/秒**到 GPU 的 **78.9 切片/秒**（fp16，显存峰值 1243 MB）。**「某个源没有 X」不等于「没有 X」**

### ADR-036: PDF 解析主路径改用 C 库，pdfplumber 降级为兜底

- **状态**: 提议
- **背景**: 解析是纯 Python 实现时的速度天花板。pdfplumber 逐页构造对象树，吞吐在个位数到几十页每秒，装机量级下解析一段就要以小时计
- **选项**:
  - A. 维持 pdfplumber 单一路径 —— 表格与复杂版式提取质量好；代价是建库解析段无法收敛
  - B. 主路径改用 PyMuPDF 这类 C 库，pdfplumber 保留为表格与复杂版式的兜底 —— 常见文档走快路径；代价是要维护两条解析路径并保证两者产出的锚点一致
  - C. 换成云端文档解析服务 —— 质量与速度都好；代价是文档内容出本机
- **决策**: 选 B
- **理由**: 「数据全本地」这条承诺排除了云端解析；本地路径里只有换掉语言层的实现才能动量级，而表格提取的少数场景交给兜底路径即可，两条路径共用同一套锚点结构以保证索引一致

### ADR-037: 用户编辑与自动重编译按段落级合并

- **状态**: 提议
- **背景**: 页面由模型编译、用户可编辑。两者都成立时，重编译不能简单覆盖整页，也不能因为用户改了一处就冻结整页
- **选项**:
  - A. 整页保护 —— 用户编辑过的页面不参与重编译 —— 最安全；代价是用户没改的部分也永远停在旧版本
  - B. 段落级合并 —— 页面正文按段落记归属，重编译只替换模型生成的段落 —— 系统段落始终新鲜，用户段落一字不动；代价是要给每个段落记归属
  - C. 按字段合并 —— 标题、摘要、要点分别判断是否被改过 —— 粒度粗；语义编辑很难归到某个字段
- **决策**: 选 B
- **理由**: 页面结构本来就要拆成标题、摘要、要点与出处四部分，段落归属与结论的出处锚点是同一套块级机制，边际成本低；而整页保护会让页面随时间越来越旧，与「核心层结论稳定」的定位冲突

### ADR-038: 情景事件按条数与时间双上限淘汰

- **状态**: 提议
- **背景**: 情景事件逐轮增长，含用户提问内容，既是磁盘增长点也是隐私暴露面
- **选项**:
  - A. 只按条数上限 —— 简单；代价是时间维度无约束
  - B. 条数与时间双上限，先到先淘汰，淘汰时只计数 —— 容量与暴露期都有界；代价是极老的项目场景会被清掉
  - C. 不自动淘汰，靠用户手动清理 —— 保留最完整；代价是数据量与暴露期均无上限
- **决策**: 选 B，上限取 5000 条与 180 天
- **理由**: 整合层的归纳窗口本来就只看最近若干轮，老事件对归纳没有价值；条数上限兜住突发增长，时间上限兜住低频使用的长期积累；淘汰时计数而不记原文，避免淘汰动作本身变成新的原文副本

### ADR-039: 归纳产出分级生效，规律需确认

- **状态**: 提议
- **背景**: 整合层从情景事件归纳出实体与规律。实体是文档中客观存在的名词，规律是跨事件推断出来的结论，两者的可信度不同
- **选项**:
  - A. 全部自动生效，用户可在图谱里删除 —— 语义记忆即时可用；代价是错的规律会带偏回答，直接损伤准确度承诺
  - B. 全部需审核才生效 —— 语义记忆最干净；代价是普通用户不会去审阅，功能等于空转
  - C. 分级 —— 实体自动生效，规律先落库为待审，未经确认不计入作答证据 —— 两者兼得；代价是要多一个待审状态与确认入口
- **决策**: 选 C
- **理由**: 准确度承诺不允许把没把握的推断直接送进答案，而目标用户不具备专业判读能力、也不会主动审阅；分级让客观事实即时可用，把需要判断的部分留在待审区

### ADR-040: 冲突判定用前置规则筛选，高风险场景强制判定

- **状态**: 提议
- **背景**: 冲突判定是一次独立的模型调用，每次作答都做会持续付出延迟与调用成本；但完全按需触发又可能漏掉关键场景
- **选项**:
  - A. 每次都判定 —— 一致性最强；代价是每次问答都多一次模型调用
  - B. 只在规则命中时判定 —— 最省；代价是断言写得含糊时检不出来，冲突静默漏过
  - C. 前置规则筛选加高风险强制 —— 命中具体断言，或所问内容涉及制度、合同、金额时强制判定，其余跳过 —— 大部分问答省掉调用，关键场景不漏
- **决策**: 选 C
- **理由**: 「知识库优先」这条承诺的风险集中在断言型回答上，前置规则正好圈出这类；涉及制度、合同、金额的问题即使回答措辞含糊也要判，因为这类答错的代价最大

### ADR-041: 术语上下文取自原文，不生成术语解释

- **状态**: 提议
- **背景**: 目标用户可能看不懂资料里的专业术语。给出解释有两种做法：模型生成，或展示原文上下文
- **选项**:
  - A. 模型生成解释 —— 对普通人最省心；代价是引入了产品第一次出现的、无法核验的生成内容，且解释可能与原文不符
  - B. 展示该词在原文中的上下文 —— 内容直接来自知识库，可回溯到页码；代价是用户要多点一次
  - C. 不处理术语 —— 零成本；代价是普通人看到术语仍然无从下手
- **决策**: 选 B
- **理由**: 产品的全部价值建立在「答案可核验」上，术语解释若由模型生成，就等于在答案里塞了一段用户无法核验的文字；上下文本来就躺在知识库里，展示它既解了困惑又不破坏承诺

### ADR-042: 摄入侧不算没人读的稀疏通道，批大小可配，int8 是设置而非默认

- **状态**: 提议
- **背景**: ADR-035 选了 GPU 路线，但**目标机器上不一定有 CUDA 版 torch**——CPU 版 wheel 装惯了是常态（这正是 TASK-053 要说清的事）。没有 GPU 就没有 fp16，嵌入就只能靠 CPU，而 CPU 上的每一分都得自己挣。真实工作域实测把「慢」拆开了三块：①**bge-m3 的 lexical_weights 每一批都在算、每一列都在写，而检索侧从来不读它**（稀疏通道早就是 tantivy 全文索引了）；②批大小硬编码成 8，每次前向的开销摊在 8 条上；③切片长短不一，一批要 padding 到最长那条，白算。第三块**比看上去难**：把切片按长度排序再切成等大的批，padding 反而**更大了**——一批 32 条在排序后的序列里跨得更远，每条都要补到那批里最长的那条
- **选项**:
  - A. 什么都不动 —— 零风险；代价是 CPU 上的建库慢到没有实用性
  - B. 关掉摄入侧的稀疏通道（留一个设置能打开）、批大小改成配置（默认 32）、**按长度分窗**、超时跟着批大小走 —— 都是「少算一点」，不换模型也不动 schema；代价是向量本身一个字节没变
  - C. 换更小的嵌入模型（如 bge-small-zh-v1.5）—— 实测快约 19 倍；代价是向量维度从 1024 变成 512，**已有的库全部要重建**，而且检索质量换了一个模型来承担
  - D. int8 量化 —— 实测快约一倍；代价是向量会有一点点位移，这是「检索准不准」的事，不该由实现替用户决定
- **决策**: 选 B 与 D。**稀疏通道默认关、批大小可配（32）、按长度分窗、超时随批大小伸缩**；**int8 做成设置**（`YUANWORK_EMBEDDING_QUANTIZE=int8`），默认 `none`
- **理由**: B 这一组改的全是「白算的活」——不必要的不写、padding 不白算——向量一个字节没变，检索质量一分没掉。**「分窗」不是「分桶」**：排序之后还要按长度**比值**切窗（下一条比窗里最短的长两倍就开新窗），否则批一大就跨进长尾里，padding 反而更大——实测真实切片，不排序切批 8 的 padding 是 49%，**排序后切批 32 是 74%（更差）**，分窗之后是 17%。**稀疏通道这一项的价值要说准**：它的**模型侧开销是噪声**（实测快 1.008 倍——5.6 亿参数的稠密前向把稀疏头盖住了），**真正的开销在写出侧**（每个切片序列化一次 JSON，一百万片 54 秒；每千片占 2.6 MB，一百万片 2.6 GB）。所以它省的是**磁盘与一次序列化**，不是时间。D 也能白拿一倍，但它动的是向量本身，所以留给用户自己开。**C 不在这一轮做**：它不是优化，是换模型，牵涉 schema 维度与全量重建，是产品决定不是实现决定。**量化的失败不许变成建库的失败**——拿不到内层模型或量化抛错时原样返回模型并记一条警告
- **这一组是 CPU 路线**：GPU 路线（ADR-035）一旦装上 CUDA 版 torch 就是主路，这一组是**没有 GPU 的机器上的兜底**，也是 CPU 路线该有的样子——实测嵌入从 0.74 切片/秒到 1.09 切片/秒（快 1.48 倍）。**GPU 路线装上后（2026-11-16），实测嵌入 78.9 切片/秒**——是 CPU 优化之后的 72 倍，是这条路线**之前**的 106 倍

### ADR-043: 落库的删除与写入共用一次刷新，攒着写由索引器自己兜底

- **状态**: 提议
- **背景**: 落库路径的第二段是全文索引。实测把这一段拆开：**分词的模型加载是一次性的 0.665 秒**（预热之后每批几乎不要钱），**提交落盘 0.22 秒**——而每一批**提交了两次**：删旧版本一次、写新版本一次，两次磁盘刷新换来同一个结果。tantivy 的 writer 还有个内存上限，攒着写不能无限攒
- **选项**:
  - A. 维持每批两次提交 —— 零改动；代价是稳态落库只有 609 切片/秒，而目标（AC-P-012）是 500，看着过了其实没有余量
  - B. 删除与写入共用一次刷新，顺序保持「先删后写」—— 稳态落库到 2564 切片/秒；代价是这一批的删除与写入变成原子的（这正好是想要的：重新索引过的文档留下的是新版本）
  - C. 元数据也按批提交 —— 实测 5000 个文件省下 1.35 秒，而同一批文件的嵌入要几个钟头
- **决策**: 选 B，**不选 C**
- **理由**: B 消掉的是一次**真的多余的**磁盘刷新，稳态落库快了四倍多，而顺序「先删后写」保证语义不变。索引器另外学会**攒着写**：`add_documents(commit=False)` 把文档留在 writer 手里，攒到 1024 篇自己刷一次——writer 的内存因此有界，这一层的边界是它自己兜的，不靠调用方记得。C 那笔账算下来只有 1.35 秒，**不值得为它改事务边界**：事务边界一动，恢复建库的语义就得重新验证，而省下的时间淹没在嵌入的几个钟头里

### ADR-044: 嵌入的批由设备自己定，编码走自己的路

- **状态**: 提议
- **背景**: GPU 路线落地后（ADR-035），嵌入从瓶颈变成了「本来可以不是瓶颈」的那一段。真实工作域实测：**建库时嵌入 49.0 切片/秒，而模型单独跑能到 78.9 切片/秒**——差的那 1.6 倍不是模型的极限，是**批的形状**与**库的调用方式**吃掉的。三件事：
  - **一半的活白干**：嵌入库的 `encode()` 先跑一遍模型去探「这设备吃得下多大一批」，**把结果丢掉**，然后把同一批**再跑一遍**才算数。我们每批切得小（实测均批 21 条），于是**每一批都算了两遍**
  - **批的大小跟设备无关**：批大小是配置里的一个数字（32）。6 GB 的卡和 24 GB 的卡拿同一个数；卡上只用了 1243 MB / 6144 MB，**八成的显存空着**
  - **向量绕了一圈**：前向出来的是 numpy 数组，转成 Python 浮点列表（每片 1024 个对象）再转回数组交给 Arrow——一批 256 片就是 26 万个 Python 对象
  - 用户的原话：**「尽可能发挥现存的能力，以适配不同的设备，而不是只针对本设备」**。写死一个批大小就是只针对本设备
- **选项**:
  - A. 只把配置里的批大小调大 —— 换一台机器就得重调一遍，而「这台机器」这件事本来就该由机器自己说
  - B. **自己拿模型前向**：一次分词、按长度排序、按**设备实测的**预算切批、OOM 就切半、向量直接留在数组里
  - C. 换一个更小的模型 —— 那是换模型，牵涉向量维度与全量重建，是产品决定不是实现决定
  - D. 升级嵌入库 —— 装的是能装上的那一版；库内部怎么切批不由我们说了算，改不动就是改不动
- **决策**: 选 B
- **理由**:
  - **批的形状跟着设备走，而不是跟着配置走**。批的大小按**填充后的 token 数**算（有几条 × 最长的那条有多长），因为设备要扛的是这个；切批时再按长度比值分开（比窗里最短的长 3 倍就开新窗），免得一批里混着一句话和一页纸——那批的每一条都要补到最长的那条。预算**先猜后量**：第一批按保守的估计切，跑完**量出这台设备一个填充 token 占多少显存**，后面的批就按这个预算切满。**显存不够时切半重来**，而且后面的批跟着变小
  - **这跟机器无关**：显卡按显存算，CPU 按核数算。同一份代码在 3060 上和在没有显卡的机器上都能跑，差别只是批多大——而这个差别是**量出来的**，不是猜的
  - **不再重复计算**：自己前向，那次「探显存」的前向就没了
  - **向量不再绕 Python 对象**：前向出来是什么就写什么
  - **库的路仍然留着**：嵌入器的内部结构对不上时（换了库的版本）退回库自己的调用；稀疏通道也走库自己的路（检索侧早就不读那一列了，它是遗留选项）
  - **配置项从「计划」变成「上限」**：`YUANWORK_EMBEDDING_BATCH_SIZE` 默认 **0 = 设备自己定**；填一个数就是「不超过这么多」，设备仍然可以自己往小里走（它说了算），但不会往大里走
- **代价**: 多了一处要跟嵌入库内部结构耦合的地方。所以这条路的入口是**能自己前向才走**，走不了就退回库自己的路——库换版本不会把建库带崩
- **踩过的坑（这一条比决策本身更值得记下来）**:
  - **「把显存用满」是错的**。第一版按显存算预算，量出「一个填充 token 值多少显存」就把批填满——**真实工作域一跑就把 3060 撑爆了**（`memory allocation failed with OOM on device 0, free: 0`）。原因是**注意力的内存随切片长度的平方涨**：一批 300 条、每条 512 token，注意力矩阵要 300×16×512×512×2 ≈ **2.5 GB**，加上模型权重与缓存就满了。**所以条数必须封顶**（实测 32 到 64 条一批最快——padding 的代价比并行度买到的多），宽度交给 token 预算管
  - **PyTorch 有两种说法**：「CUDA out of memory」和「memory allocation failed with OOM」。**只认前一种，第二种会被当成普通异常抛出去**，OOM 切半的兜底根本不触发。两种都要认
  - **前向必须关掉 autograd**。自己前向时若忘了 `torch.inference_mode()`，**每一层的中间结果都被留在显存里等着反向传播**：实测 bge-m3 上**每个 token 要 776 KB**，关掉之后只要 **22 KB**——**35 倍**。后果不是「慢一点」，而是**批根本装不下**（64 条 × 512 token 在关掉之前要 14 GB，在关掉之后只要 704 MB）。嵌入库自己的路有 `@torch.no_grad()`，自己写的那条要自己记得

### ADR-045: 本项目的可写状态归到一个可配置的根目录

- **状态**: 提议
- **背景**: 这台机器的系统盘（C 盘，200 GB）只剩 **4.2 GB**。而本项目在系统盘上的足迹几乎全是**模型缓存**：`~/.cache/huggingface` 里的 `hub/` 是 **4.70 GB**（bge-m3 加上重排模型）——**那是本项目下载的模型，却落在系统盘上**，而本项目管不着它（那是 HuggingFace 自己的默认目录）。另外三件事：
  - **索引写在快满的盘上会更慢**：实测 C 盘只剩 4 GB 时，建库的落库阶段明显变慢（AC-P-012 的 500 切片/秒直接受影响）
  - **数据目录跟着 cwd 跑**：`.env` 里 `YUANWORK_DATA_DIR=./data` 是**相对路径**，而后端的 cwd 在三种启动方式下各不相同（桌面端是 `src/backend`，从仓库根手动跑是仓库根，从 `src/backend` 手动跑又是 `src/backend`）→ **同一个项目有三套不同的知识库**。实测 `src/backend/data` 与仓库根的 `data/` 各躺着一份 store.db
  - **模型缓存的落点必须在导入前定**：huggingface_hub 的 `HF_HOME` 是**导入时**算出来的常量，导入之后再设环境变量**不生效**。实测：先设 `HF_HOME` 再导入 → 生效（`HF_HUB_CACHE` 指向新目录）；先导入再设 → 不生效。而本项目的嵌入模型是懒加载的（函数内 import），所以只要在进程最早期把环境变量摆好就来得及——前提是**没有别的库提前把它拉进来**（实测 litellm 不会）
- **选项**:
  - A. 只在 `.env` 里写绝对路径 —— 能救这台机器，但换个 cwd、换个启动方式仍可能落到别处；模型缓存仍然不在项目手里
  - B. **一个根目录 `YUANWORK_HOME`**，下面分 `data/`（索引、日志、审计）与 `models/`（模型缓存）；根目录由环境变量指定，模型缓存目录同时写进 `HF_HOME`
  - C. 模型缓存交给系统的 `HF_HOME`，项目不管 —— 项目仍然无法保证自己的大文件不落在系统盘上
  - D. 代码里判断系统盘剩余空间，不够就自动改道 —— 隐式行为，用户猜不到自己的东西在哪，也没法备份
- **决策**: 选 B
- **理由**:
  - **一个旋钮搬走全部**：`YUANWORK_HOME` 一设，索引与模型缓存一起搬（`YUANWORK_HOME` 目录下的 `data/` 与 `models/`）。`YUANWORK_DATA_DIR` 仍可单独覆盖索引目录（桌面端已经在用它，不破坏）
  - **模型缓存写进 `HF_HOME`**：本项目下载的模型就该由本项目管。用户自己设了 `HF_HOME` / `HUGGINGFACE_HUB_CACHE` 就不覆盖——那是他的选择，不是本项目该改的
  - **落点在导入前定**：`HF_HOME` 是导入时算的常量，所以这件事必须在进程最早期做（`yuanwork/__init__.py`），而不是等到加载模型时。**这一条是本决策里最容易做错的地方**：晚一步设置不报错，只是静默不生效，模型照样下到旧目录
  - **不用隐式改道**：东西在哪必须看得见、说得出口，否则「备份」「清理磁盘」「换机器」这三件事都没法做
- **代价**: 多了一个目录概念；数据目录的默认值从 `~/.yuanwork` 变成 `~/.yuanwork/data`——**老目录要一次性搬迁**（启动时自动搬，搬完不删原目录）
- **边界**:
  - 用户设了 `HF_HOME` / `HUGGINGFACE_HUB_CACHE` → **不覆盖**
  - 用户设了 `YUANWORK_DATA_DIR` → 索引目录用它，**赢过** `YUANWORK_HOME` 目录下的 `data/`
  - 桌面端：只有在用户**既没设 `YUANWORK_DATA_DIR` 也没设 `YUANWORK_HOME`** 时，才把索引指到项目目录的 `data/`
  - 相对路径仍然允许（用户可以写相对路径），但**一律按进程启动目录解析成绝对路径**再用——同一个项目只有一套知识库

### ADR-046: 切片的长度用模型读得下的 token 量

- **状态**: 提议
- **背景**: 切片器按**字符**切（`MAX_CHARS = 2000`，注释写着「~500 tokens」——**那是英文的换算**），嵌入器按 **token** 读（`embedding_max_tokens = 512`）。**两把尺子不一样**，差出来的部分就是检索不到的内容。
  - 实测真实工作域的 **4801 个切片**：token 数中位 103、p90 508、p99 934、**最大 1385**；**471 个（9.8%）超过 512**，这些切片的尾巴合计**占全部内容的 10.6%**
  - **丢掉的内容不是「弱一点」，是「彻底看不见」**：只读前 512 token 的向量，与**自己后半段**的余弦是 **0.689**；与**毫不相关**的切片是 **0.854**——**分差为负**。全文索引存的是全文，关键词还能捞到，但语义通道里那段内容比噪声还远
  - **让模型读全文救不了**：全文向量与自己尾部的余弦是 **0.689**，和只读头时**一模一样**——长文本池化成一个向量，头尾在向量空间里天然离得远。**病根是「块太长」，不是「读得太短」**
  - **切短就能救**：按 512 token 切开之后，针对尾部内容的提问，**top-10 命中率 69.4% → 98.5%**（top-3 46.7% → 93.6%）
  - 代价：块数 4801 → **5291（+10.2%）**，token 总量不变（只多了重叠）；嵌入慢约 10%
- **选项**:
  - A. 把 `embedding_max_tokens` 提到 2048 —— **实测救不了**（全文向量对尾部同样失明），只是让模型白读
  - B. **切片器按 token 切**，上限就是嵌入器的读取长度
  - C. 切片器继续按字符切，把上限降到最坏情况（中文 1 字约 1 token → 510 字符）——英文会碎成四分之一，模型一半的读长度被浪费
  - D. 长块拆成多块、每块一条向量、但仍按原块存文本 —— 等价于 B，却把「块」和「向量」的对应关系搅乱，引用会指不准
- **决策**: 选 B
- **理由**:
  - **切块器与嵌入器用同一把尺子**：`YUANWORK_EMBEDDING_MAX_TOKENS` 一个数，两处都用它。**尺子只有一个，就不会再对不上**
  - **要真 tokenizer**（就是嵌入模型那个）：估算只能兜底，且**故意往大了估**——块小了只慢一点，块大了丢尾巴
  - **切块在主进程里做**（只有解析在工人进程），所以 tokenizer 只加载一次（3.2 秒，含 `transformers` 的首次 import；跑应用时它本来就被 import 了）
  - **多出来的 10% 块不是浪费**：它们就是**原来被丢掉的那部分内容**，现在各自有了向量
- **代价**: 切块器从此依赖嵌入模型的 tokenizer（同一个模型，不是新的耦合）；**没有模型缓存的机器走估算兜底**，切出来的块与有 tokenizer 时不完全一样（同样的内容，块数可能差几个百分点）
- **踩过的坑**:
  - **特殊 token 要占位置**：模型的分隔符（开头结尾各一个）占 2 个位置，所以**内容上限是 510 而不是 512**
  - **字符数不是 token 数**：中文 1 字符约 0.7–1 token，英文 1 字符约 0.25 token——「2000 字符 ≈ 500 token」只在英文里成立
  - **长文本池化成一个向量，头尾天然离得远**——所以「让模型读全文」**不能**替代「把块切短」。**先量清楚「丢的是弱一点还是彻底没了」，再决定怎么修**

### ADR-047: 问题点名了文件，证据就锁定那份文件；总结看的是它的铺开

- **状态**: 提议
- **背景**: 用户问「总结一下人工智能导论（第五讲）24.pdf 的内容」——**这份文件就在工作域里**
  （已索引 4364 个文件），回答却是「证据不足，无法正常回答」。查出三件事，**一件叠着一件**：
  - **核心层的短路不看文件线索**（ADR-031/034）：核心层找到两条**别的文档**的结论就返回了，
    长尾层根本没搜。短路是**速度**的优化，不是正确性的保证——用它回答「关于这份文件」的问题，
    答的其实是**另一份文件**
  - **文件名对不上**：索引里存的是「人工智能导论（第五讲） 24.pdf」（文件名的第五讲后面有个空格），
    问题里写的是「…（第五讲）24.pdf」→ SQL 的 `file_name = ?` 匹配不到 → 定位步骤**根本没锁定**那份文件
  - **总结要的是铺开**：10 条最像问题的切片说不出一份 150 页的文档讲了什么——而「总结这份文件」这个问题
    本身就是文件名，相似度排序对它说不了什么
- **选项**:
  - A. 不管 —— 核心层有结论就用（速度优先），名字对不上就当没点名
  - B. **问题点名了文件就把检索范围锁定到那份文件**：核心层的证据只取来自那份文件的结论；
    长尾层**在那份文件里**搜；总结类问题改为**按文档铺开**取证据（20 条，均匀分布在全文），
    并让证据闸知道这是「总结一份文件」
  - C. 只修名字匹配，范围不动
- **决策**: 选 B
- **理由**:
  - **点名的文件是读者要的答案，不是线索**。读者说「这份文件」，系统就该从这份文件里答；
    拿另一份文件的结论回答，读者核对的却是自己没问的那份文件
  - **名字对不上不该让用户重打一遍**：文件名里的空格与大小写是**文件系统的事**，不是读者的意思
    → 匹配时忽略空格与大小写（`REPLACE(LOWER(file_name), ' ', '')`）
  - **铺开才说得清一份文档讲了什么**：证据取 20 条、均匀分布在全文（从第一段到最后一段），
    而不是取最像问题的那几段；每一段都带锚点，读者仍能逐条核对（AC-F-009 的精神）
  - **闸门要认得「总结一份文件」**：证据来自那份文件、并且覆盖了它的多个部分，就算充分
    （这条写在 `evidence_gate.j2` 的第一条，是模型自评闸的一条判据，不是硬规则）
- **代价**:
  - 点名文件时要搜一次长尾——但**搜的是一个文件**，不是全库（实测一份文件的切片扫描 0.09 秒），
    所以 AC-P-009 的两秒预算不受影响（AC-P-009 的措辞为此加了一处例外）
  - 核心层那份文件的结论会与切片一起进证据集——两者来自**同一份文件**，不构成层间冲突
    （ADR-034 的层间冲突判定不受影响）
- **与 AC-P-009 的关系**: AC-P-009 讲的是「核心层页面已有**可用**结论」的情形。点名了文件时，
  别的文档的结论**不可用**；而那份文件自己的结论（每份文档只有寥寥几条）**不足以**回答
  「这份文件讲了什么」——因此长尾层照搜，且只在那份文件里搜

### ADR-048: 拒答的位置给两遍——文案一遍，字段一遍

- **状态**: 提议
- **背景**: 拒答里的「最可能相关的位置」是**文字**：读者看得到文件名与页码，**却点不开**。
  用户报「上面的位置没有连接，无法点击跳转」——位置写着「去看第 12 页」，但读者得自己去翻目录找那份文件。
  麻烦在于 ADR-012 要求位置表述用人读得懂的形式（文件名 + 页码或章节名），
  **不用路径片段**——而能打开东西的正是路径
- **选项**:
  - A. 文案里带上路径 —— 违反 ADR-012；路径是内部标识，对不熟悉资料的人没有意义，还把目录结构露给读者
  - B. **位置给两遍**：文案里照旧（人读），另外给一个带路径的字段（程序用）；
    桌面端把文案里的清单换成**可点的按钮**，其余读者拿到的还是那份文字清单
  - C. 只给字段，不要文案里的清单 —— 桌面端干净；但接口的其他读者（脚本、将来的别的端）就看不到位置了，
    ADR-012 的承诺落空
- **决策**: 选 B
- **理由**:
  - **同一件事，两种读者**：文案是给**人**的（「《合同.pdf》（第 12 页）」），字段是给**程序**的
    （带路径，能真的打开）。ADR-012 的「不用路径片段」说的是**文案**，不是字段
  - **桌面端上两份说的是同一件事**：所以那里用按钮替掉文字清单，读者只看一遍；
    认不出文案的结构时宁可两份都显示——**宁可重复，不可丢失**
  - 按钮点了之后照旧由应用说出位置（「已打开《示例实验.pdf》· 第 10 页」），
    因为默认程序（WPS）未必会跳页（AC-F-006）
- **代价**: 问答结果多一个字段（`refusal_positions`）；桌面端要认得文案里的标题
  （`## 最可能相关的位置` 与 `## 你可以：`），认不出就退回显示全文

### ADR-049: 回答按 Markdown 渲染，术语在渲染之后放回去

- **状态**: 提议
- **背景**: 回答本来就是 Markdown——模型这么写，拒答的模板也这么写——但对话区把它当**纯文本**显示，
  于是读者看到的是**标记本身**：「## 你可以：」「**补上另一份文档**」。
  模板里的 `##` 是给 Markdown 渲染器看的标题，给读者看就是格式坏了。
- **选项**:
  - A. 模板与提示词都不写 Markdown（改成纯文本） —— 不用渲染器；代价是模型仍然会写 Markdown
    （提示词管不住模型的格式习惯），而且表格、代码块、分级标题这些信息**真的丢了**
  - B. **用 Markdown 渲染器渲染回答**，术语在渲染**之后**放回可点的按钮
  - C. 自己写一个小的渲染器 —— 不引依赖；代价是表格、代码块、嵌套列表这些都要自己写一遍，
    而且写出来的不是 Markdown，是「像 Markdown 的东西」
- **决策**: 选 B
- **理由**:
  - **格式是内容的一部分**：模型用标题分节、用列表列步骤、用表格对比，
    这些结构本身就是答案的组织方式；压成纯文本是把答案的一部分扔掉
  - **术语必须在渲染之后放回去**（AC-F-030）：术语出现在**渲染后**的文本节点里
    （一个段落、一个加粗、一条列表项都可能含术语）。若在 Markdown **源码**里替换，
    代码块里的术语会变成链接——代码块里显示的是链接而不是那个词
  - **回答里的链接不点走**：链接只显示地址。一个本地应用不能被一条链接带到别处去；
    回答里的图片同理——不取（那是对别处的一次请求）
- **代价**: 前端多一个依赖（`remark-gfm`，表格/删除线/任务列表要它），包大了约 45 KB；
  **流式输出时每来一个 token 都要把整段重新解析一遍**（回答只有几 KB，代价随回答长度线性增长）

### ADR-050: 索引是真相，账本只是账本

- **状态**: 提议
- **背景**: 用户报「总结一下 示例文档.md 中的内容」被拒答，而侧栏明明写着这个文件已索引、13 个切片。
  查出来三件事叠在一起：
  - **账本先记「已入库」，向量后写**：批量建库把切片攒着写（ADR-043），而 SQLite 的账本**每个文件读完就更新**。
    建库被打断（应用被强杀 → 后端跟着死 → 内存里那一批切片没了）时，
    **账本说这个文件有 13 个切片，索引里一个都没有**
  - **提问时看不出区别**：检索返回 0 条证据 → 证据闸按规矩拒答 → 「证据不足」。
    可事实是「你问的那份文件根本没进索引」——**两件事，读者却拿到同一个说法**
  - **重建也修不好**：建库判断「已索引就跳过」看的是**账本**，于是它把那个文件跳过了——
    缺口**不可修复**，只能靠手工删了重来
- **选项**:
  - A. 账本说了算（现状）—— 简单；代价是缺口既说不清也修不好
  - B. **索引说了算**：判断「是否已入库」看**索引里有没有这个文档**；
    提问时若文件在账本里却不在索引里，拒答要说这件事；界面报告索引与账本的差额
  - C. 建库时把账本更新挪到切片写完之后 —— 被打断的建库不再留下假账；
    但**已经**留下的假账还在，缺口依然不可修复
- **决策**: 选 B（并顺手做 C 的一半：批量的账本更新跟着写入走）
- **理由**:
  - **索引是读者能用到的东西**：账本说「已入库」，读者要的是「搜得到」；
    两者不一致时，**以索引为准**——它是检索真正读的那一份
  - **不可修复的缺口比难看的拒答更糟**：缺口让「重建」这个按钮失去意义
    （重建跳过它 ✗）——所以判断依据必须换
  - **说法要跟事实对得上**：读者问的是「这份文件里有什么」，系统答「知识库里没有足够证据」，
    是在说一件**不成立**的事；实情是「这份文件没进索引，重建一次就好」——**一句话就能解决的事，不该说成一句无解的话**
  - **差额要说出来**：侧栏的「已索引 N 个文件 · M 个切片」来自账本；
    账本撒谎时，数字就骗人——所以差额直接写出来
- **代价**: 建库开始时要把索引里的文档号读一遍（只读一列，**4360 个文档 0.19 秒** ✓）；
  提问时多一次「这个文件在索引里吗」的检查（一次过滤扫描，约 0.09 秒 ✓）；
  多一个拒答理由（`index_missing`）与一句文案
- **实测**: 修完后那次重建把 4 个缺口的文件补了回去——账本 62139 个切片、索引 62139 个切片，
  **分毫不差** ✓；同一个问题随即正常作答（13 条引用）✓

### ADR-051: 重建不必读它不必读的文件

- **状态**: 提议
- **背景**: 用户问「加一个文件要多久」。实测：**加一个文件触发一次全工作域重建，137 秒**，
  而那个新文件自己只占几秒——**时间几乎全花在把 4413 个文件重新走一遍**：
  建库对每个文件算 SHA-256（**读它的每一个字节**）才发现「没变」。
  算哈希是 4 GB 的读取，换来的是一个答案——而**账本里已经有这个答案了**：
  账本记着这个文件多大、**什么时候读的**
- **选项**:
  - A. 照旧 —— 每个文件都算哈希；代价：每次重建多花一分钟，而这些文件一个都没变
  - B. **先问账本**：文件的大小一样、且**读它之后没有被碰过**（文件的修改时间不晚于账本读它的时间）
    → 内容不可能变，**不必读**；不一样才去算哈希
  - C. 把文件的修改时间单独存一列 —— 更直白；代价是改表结构、要迁移老库，
    而账本里已有的「读它的时间」够用了
- **决策**: 选 B
- **理由**:
  - **账本记的是「我什么时候读的」**——那正是「这个文件后来被动过吗」的答案
  - **代价是一次 stat，不是一次全文件读取**：把每个文件的「读 4 GB」换成「看一眼大小和修改时间」
  - **这是每个构建工具都做的取舍**（make、rsync、git 的索引）：**改了内容但没改大小、
    又把时间戳改回去**的编辑认不出来。认出它要读每个文件的每一个字节——代价是每次重建一分钟
  - **算哈希挪进线程**：算哈希是同步的读文件，放在事件循环里会**卡住整个后端**
    （重建期间聊天不响应、连进度都查不到）；挪进线程之后，后端在重建期间照常能答
- **代价**: 上面那条取舍；以及**读与写之间被改过的文件**（建库正在读的时候有人改了它）
  要等到下一次编辑才会被发现
- **实测**: 建库为每个文件做的那个检查（续上的判断），**从 13 秒降到 1.8 秒**
  （4412 个文件，同一台机器上连着量的：这台机器的速度本身会飘，所以两个数要一起量）。
  **重建的两分钟大半不在这儿**：工作域里有 15 万个文件（能索引的 4412 个），
  **把工作域走一遍要 20 秒**，而且要走**两遍**（一次数文件、一次真的建库）；
  剩下的时间是真在索引那些新增的文件（解析 + 嵌入）

### ADR-052: 重建只走一遍工作域，分母由作业自己说

- **状态**: 提议
- **背景**: 用户问「加一个文件要多久」。ADR-051 之后，续上的判断已经不读文件了，
  但**把工作域走一遍**还是 20 秒——而且**走两遍**：`POST /ingest/rebuild`
  先数一遍文件（好让回答里有个数），后台作业建库时再走一遍。
  工作域里是 **15 万 775 个文件**（能索引的只有 4412 个），
  一遍走完要 **20.9~22.9 秒**（同一台机器上连着量的两遍，这台机器速度本身会飘）。
  两遍就是 **~44 秒**——而这一遍 20 秒的目录遍历是**同步的磁盘 I/O**，
  它就发生在事件循环里：**重建刚开始的 20 秒，后端答不出任何东西**
  （聊天不响应、连进度都查不到，桌面端靠 20 秒超时 + 容忍 15 次连续超时撑着）。
  界面上的症状是：点「重建」之后有二十来秒只有一句「正在准备…」，像是卡住了
- **选项**:
  - A. 照旧 —— 两遍；代价：那 20 秒的遍历仍在请求路径上，卡顿仍在
  - B. **请求数一遍，把清单交给作业** → 只走一遍；
    代价：作业建库在**点击那一刻的快照**上——点击与开工之间新加的文件，
    这一轮永远进不了索引，而「重建」的全部意义就是捡起新加的文件
  - C. **作业自己走一遍，自己发布分母**：请求立刻回答（毫秒级），
    作业在读第一个文件之前把「有多少活」写进行里；
    代价：分母晚 ~20 秒到达，界面先显示「正在统计工作域…」
- **决策**: 选 C
- **理由**:
  - **数与做必须是同一次枚举**——否则「数的那批」与「读的那批」永远是两批，
    中间夹着的时间窗里工作域变了，两批就对不上
  - **请求不该替作业数文件**：数文件要 20 秒，把这 20 秒放在请求路径上，
    就是把「点一下没反应」这件事换个说法
  - **遍历必须离开事件循环**：20 秒的同步目录 I/O 放在事件循环里会卡住整个后端
    ——与 ADR-051 把算哈希挪进线程是同一条理由
  - **「不知道」要写成「不知道」**：`files_queued` 填 0 是在说谎
    （0 在这个接口里已经有确定含义：工作域里没有可索引的文件），
    而这次排的偏偏有 4413 个文件；改成 `null`（「还没数」）之后，
    谎话变成了一句事实陈述
- **代价**: 分母晚 ~20 秒到达（界面从「正在索引 4412 个文件…」变成「正在统计工作域…」）；
  `files_queued` 对重建这条路变成可空——这是接口契约的变更，
  应用内唯一的读取点与两个 bench 脚本随之改
- **实测**: 省掉一整遍遍历 = **~21~22 秒**（实测 20.9~22.9 秒）；
  请求的应答时间从 **~21 秒变成 ~10 毫秒**。
  另外**没有算进去**：剩下那 ~20 秒就是这一遍遍历本身，
  它里面最大的可省项是 `f.is_file()` 对 17 万个 rglob 条目各做一次 stat
  （实测带 is_file 22.47 秒 vs 不带 14.72 秒，差 6~8 秒）——
  **这次不做**：把 rglob 换成 `os.scandir` 能白拿这 6~8 秒，
  但 Windows 上 `DirEntry.is_dir(follow_symlinks=False)` 对 junction（目录联接）返回 False，
  会把 junction 底下的文件整个漏掉，这个坑比 8 秒贵。留给下一个任务，
  用真实工作域验一遍 junction 再上

### ADR-053: 推理轨迹显示在右栏，且只显示步骤与结果，不显示模型的话

- **状态**: 提议
- **背景**: 右栏「推理轨迹」页是一句占位说明「阶段 2 将可视化 3 步推理轨迹」，
  底下画的却是**最近 3 条对话消息**（角色、预览、置信度）——那不是轨迹。
  后端其实早就在发轨迹了：`AgentLoop._stream_steps` 依次发 7 个 `trace` 事件
  （understand / localize / extract / wiki_compile / gate / answer /
  check_conflicts），每个带 `status` 与该步的结果（候选文件、证据条数、
  闸门判定、置信度、拒没拒、冲突几处）；`done` 事件里的 `response.trace`
  还带着每步的完整结果。前端把 `trace` 事件**直接丢掉了**：
  `ChatWindow` 的事件分支只处理 token / answer / citations / done /
  refusal / conflict / error。于是读者看到的是一句没兑现的承诺
- **选项**:
  - A. 照旧 —— 保留占位说明；代价：承诺继续挂着，而它背后的事件早就在流里
  - B. **右栏按步累积 SSE 的 `trace` 事件**：7 步固定顺序实时显示，
    每步显示状态与该步的结果计数或判定结论；
    **不显示模型的理解文本**（那是模型的话，不是事实）
  - C. 把轨迹铺进对话区，每步一条消息 —— 代价：对话流是给答案的，
    过程消息会把它冲淡；轨迹是过程，不是回答
- **决策**: 选 B
- **理由**:
  - **轨迹的价值是让读者看见这一步拿到了什么**（定位到几个候选文件、抽出几条证据、
    闸门放不放、答没答、冲突几处），不是让读者读模型的理解——
    用户报的「没看到有什么作用」正是这个
  - **步序固定**，读者才知道自己在哪一步；顺序乱了，轨迹就只是日志
  - **事件已经在流里**，前端只是没接——接上是零后端改动的活
  - **只显示计数与判定**：读者普遍缺少判读能力（ASM-012），
    把模型的理解摆出来等于把模型的话当成事实摆在读者面前
- **代价**:
  - 前端 store 要多存一份「本次运行的步骤」，新一轮提问开始时清空
  - `understand` 那步的 `output` 里 `topic` 可能是提问的前 50 字——
    所以右栏不显示 output 文本，只显示状态与计数
  - 后端不用改，但 `trace` 事件的字段以后会变（加字段），右栏要跟着认

### ADR-054: 图谱的边只取有依据的关系，没有关系就说没有

- **状态**: 提议
- **背景**: 用户报「图谱有什么作用」。实测那张图是 **136 个节点、0 条边**
  （36 个页面 + 100 个实体）。查出来三件事**叠在一起**:
  - `WikiGraph.build_graph` 只画 `wiki_links` 里 `target_type='page'` 的边；
    而库里那 171 条链接**全是** `page→chunk`（131 条）与 `page→doc`（40 条），
    **一条页面↔页面都没有**——编译出来的页面正文里只有 `[[来源:文件名 页码]]`
    标记，而 `WikiLinker.extract_links_from_markdown` 明确把「来源:」开头的
    当**出处**不当链接，于是 `auto_link_page` 什么也没建
  - `entity_relations`（实体之间的关系）**是空的**：整合层只归纳实体与规律，
    不写关系
  - `entity_mentions`（哪个页面提到哪个实体）**也是空的**：
    `EntityExtractor.extract_and_store` 会写它，但**没有任何地方调用它**
  于是「实体图谱」在实现里是一堆散点。而 AC-F-015 写着「SHALL 产出实体节点、
  关系边并支持图谱浏览」，验收报告里标 ✅ 通过——但验收只跑了实体存储与抽取的
  单测，**没看真机上那张图**
- **选项**:
  - A. 照旧画散点 —— 代价：图谱这个入口存在，但看不出任何关系
  - B. **边只取有依据的关系**，分三类：
    ① **库里记着的**——页面→源文件（`wiki_links` 的 `derived_from`）、
    页面↔页面（`wiki_links` 里显式的 `[[链接]]`）；
    ② **从记录里读得出的**——两页共享同一批来源切片（页面上的 `source_chunk_ids`）、
    实体的名字或别名出现在页面的标题、摘要、要点或正文里（这一页提到了这个实体）、
    两个实体被同一页提到（它们共现）；
    ③ **没有的就不画**——界面上写明「还没有关系」
  - C. 打开图谱时现算相似度边（页面两两比 embedding）—— 代价：每次开图都算一遍，
    而且**相似不是关系**；读者会把它当成关系去读
- **决策**: 选 B
- **理由**:
  - **一条画出来的边必须说得清它是什么关系**：「这个页面是从这份文件编译出来的」
    「这个页面提到了这个实体」「这两个实体在同一页出现过」。
    相似度算出来的边没有依据——它是猜的，而本项目的读者缺少判断猜得对不对的能力
  - **边从库里取，界面与数据永远是同一份**：改了库，刷新就是新的；
    不会画着旧的边，让人以为关系变了
  - **「还没有关系」是一句实话**：散点图配一句「还没有关系」，
    比一张看起来像关系网的散点图诚实
  - **文档要成为节点**：一份文档撑起 23 个页面时，直接连页会连出一团毛球；
    做成节点就是 23 条星形边——这是这 23 个页面唯一可能的连法
  - **补 AC-F-015 的另一半**：它早就承诺了「产出实体节点、关系边」，
    只是那半截没接上——现在接上，承诺才兑现
- **代价**:
  - 「页面提到实体」是**文本匹配**：会有假阳性（一个只顺带提了一词的页面也算）。
    缓解：名字太短（少于 2 个汉字 / 4 个字母）或含路径分隔符的不参与匹配；
    这类边在图例里标成「提到」——它是导航提示，不是证据
  - 边是**打开图谱时实时算的**（`WikiGraph` 本来就不落盘、每次实时构建）——
    对「重建要多久」的影响是 0（重建路径根本不调它；实测 36 页 / 193 实体
    整套推导 19 毫秒）
  - **图里的实体有上限：最多 100 个**。挑的是**被最多页提到**的那一批——
    按「被写过多少次」挑是挑不出关系的（那个计数记的是抽取次数，
    与「哪一页提到它」无关）。落选的实体不进图：它们在库里还在，
    只是不在这张图上（实测真机 193 个实体 → 进图 27 个，
    落选的那些一个页都没提到，画出来也只是一堆孤立的点）
  - **一窝超过 8 个就整窝不画**：共用同一个切片的页面、一页里提到的实体，
  同一把尺子量两件事——8 个凑在一起是 28 对，读者还跟得上；
  20 个是 190 对，那已经是毛球，不是关系了。整窝之间**不画边**
  - `entity_mentions` 与 `entity_relations` 两张表仍然是空的：
    真正的提及与关系要靠写入路径补上（编译页面时抽实体并记提及、整合时写关系），
    那是另一个任务的事；这一轮先让图里有**有依据**的边

### ADR-055: 点图谱节点是导航，不是刷新；选中只改样式，不重排

- **状态**: 提议
- **背景**: 用户报「点击蓝色的只是刷新一次」。查出来两件事:
  - **点了没反应**: 点蓝色节点 → `WikiGraphView` 调 `selectWikiPage(d.id)`，
    只是把 id 写进 store；**视图仍停在图谱**，读者看到的只是那个节点的描边变黑
    ——像刷新了一次。而侧栏「图谱」与「Wiki」本来就是同一件事的两个视图，
    点节点就该到那一页
  - **点完还重排**: 图谱的 `useEffect` 依赖 `[graph, selectedId, selectPage]`，
    `selectedId` 一变，**整个 SVG 连同力导模拟被重建**，节点重新洗牌——
    读者刚点中的那个点自己跑了
- **选项**:
  - A. 照旧 —— 代价：图谱是个只能看的风景
  - B. **点页面节点 = 切到 Wiki 视图并打开那一页**（导航）；
    选中只改节点的样式（描边/半径），**不重建模拟**——布局只在图谱数据变化时重算
  - C. 在图谱里开一个抽屉预览页面 —— 代价：抽屉又是一层界面，
    而页面本来就有自己的视图
- **决策**: 选 B
- **理由**:
  - **图谱是入口**：点节点而页面不出来，等于这个节点没有作用——
    用户报的「点蓝色的只是刷新一次」正是这个
  - **重排让读者每次都要重新找刚才那个点**：选中是**看**的动作，不该动**布局**
  - **模拟只在数据变时重算**：数据什么时候变？页面被编译、实体被归纳——
    那本来就该重画
  - **位置要记下来**：图谱与 Wiki 是两个视图，来回切是常事；
    节点位置记进 store，回来时还在原处，读者不用每次重新找
- **代价**:
  - 图谱与 Wiki 视图共用 store 里的 `selectedWikiPage`；
    从图谱跳到页面再回来，选中态还在（这正是要保留的）
  - 选中态变了不能再走「重建整个 SVG」这条路，得改成只更新样式那一层
  - 实体节点与文档节点没有「一页」可打开——点它们要说得出它是什么，
    **点不动的节点要在界面上有说法**

### ADR-056: 审计接到右栏：只显示元数据，清空是删自己的记录

- **状态**: 提议
- **背景**: 用户报「审计目前好像还没做」。**后端做完了**：`GET /api/v1/audit`
  （最近 N 条，默认 100、上限 1000）、`GET /api/v1/audit/stats`（调用次数、
  令牌数、失败数、按模型与按任务类型分组）、`DELETE /api/v1/audit`（清空）
  三个接口都在；`audit.jsonl` 里已经躺着**上千条**记录（时刻、模型、任务类型、
  提示词哈希 16 位十六进制、提示词与回答令牌数、耗时、成功与否、`error_kind`）。
  右栏「审计」页却写着「审计日志（阶段 3 启用）」——一句没兑现的承诺。
  而且那一页还说会记「**查询摘要**」——可条目里**没有摘要**，只有哈希：
  ADR-018 定的就是「只存元数据与哈希，不存提问与回答原文」。
  前端一个审计接口都没接
- **选项**:
  - A. 照旧 —— 代价：本地明明有上千条记录，读者在界面上看到的仍是一句「以后启用」
  - B. 右栏接上三个接口：一张记录表 + 汇总计数 + 一个「清空」按钮（DELETE），
    并把「查询摘要」那句改成条目里真有的字段
  - C. 审计另开一个窗口/页面 —— 代价：多一个入口；审计是「回答旁边顺手看一眼」
    的东西，不值得单开
- **决策**: 选 B
- **理由**:
  - **审计的价值是「能查」**：出问题时翻出那一次调用的模型、任务、令牌、耗时与成败
    ——它已经在本地 JSONL 里，剩下的是把它显示出来
  - **表里只有元数据**（ADR-018）：提示词以哈希出现，不出现提问与回答的原文；
    照抄「查询摘要」会让读者去找一个不存在的东西
  - **先看总量再看明细**：调用次数、令牌数、失败次数
  - **清空是删用户自己机器上的记录**，所以要**报告清掉了多少条**；
    清空失败要说失败，不能谎称已清空
- **代价**:
  - 右栏多两个请求；表格要处理后端的 `limit` 上限（1000）
  - 「清空」不可逆，按钮要有一次确认
  - 右栏只有一栏宽，列要挑：时刻、任务、模型、令牌、耗时、成败；
    `prompt_hash` 只在悬停提示里露出来
  - 桌面端的请求走 Tauri 桥，**桥接层要新增三个命令**——否则桌面端调不到后端

### 3.2 模块接口签名

#### `Workspace.add_path(path)`

- **语义**: 把一个文件夹或单个文件加入工作域
- **错误**: 路径不存在时抛出错误
- **不变量**: 同一路径只登记一次

#### `Workspace.list_entries(included_only=True)`

- **语义**: 列出工作域条目
- **错误**: 不抛异常
- **不变量**: 返回顺序按加入时间

#### `Workspace.remove_path(path)`

- **语义**: 把一个条目移出工作域
- **错误**: 条目不存在时返回「没有这一项」，不抛异常
- **不变量**: 移除条目时，一并清除只由它带来的索引条目——**清索引由工作域路由执行**（只有路由同时
  拿着关系库与语义记忆），`Workspace.remove_path` 本身只删条目行

#### `Workspace.list_files()`

- **语义**: 列出工作域覆盖到的全部文件，文件夹展开、单文件原样
- **错误**: 文件夹读不到时跳过该文件夹并记日志
- **不变量**: 被两个条目同时覆盖的文件只出现一次；
  **文件夹展开在工作线程里做**，不占事件循环（ADR-052）

#### `IngestionPipeline.ingest_file(path)`

- **语义**: 摄取一个文件并写入索引
- **错误**: 捕获异常并返回失败结果，失败原因不含堆栈
- **不变量**: 位置锚点随切片一起写入索引

#### `IngestionPipeline.build_workspace(force, on_progress)`

- **语义**: 按工作域条目建库——工作域覆盖到的全部文件并行摄取，已入库的跳过
- **错误**: 单个文件失败只记进结果，不中断整轮；不受支持或超限的文件在结果里列出原因
- **不变量**: 进度分母是**真正会处理的文件数**（受支持的），不能索引的文件只进结果的原因清单；
  内容相同的文件只入库一次；**分母在建库开始前就报出来**——第一次进度回调就带着它，
  它与这一轮的工作来自同一次枚举（ADR-052）

#### `HybridRetriever.search(query, top_k, doc_ids, file_types)`

- **语义**: 执行两路召回并融合
- **错误**: 通道不可用时降级为另一路；两路都不可用时抛出错误
- **不变量**: 每条证据都带位置锚点

#### `TierClassifier.classify(doc)`

- **语义**: 判定一份文档属核心层还是长尾层
- **错误**: 判定失败时归为长尾层并记录原因，不阻断建库
- **不变量**: 判定结果与判定来源落库；用户显式指定的分层不被改写

#### `CoreCompiler.compile(doc)`

- **语义**: 在摄入时通读核心层文档原文并编译出页面
- **错误**: 编译失败时把该文件标记为待重编译并继续处理其余文件
- **不变量**: 每条结论都带出处锚点；发现矛盾时保留两个版本

#### `TieredRetriever.search(query, top_k)`

- **语义**: 先检索核心层页面，核心层结论不足时再检索长尾层切片
- **错误**: 核心层检索不可用时降级为只查长尾层
- **不变量**: 核心层结论足够时不再触发长尾层检索

#### `EvidenceGate.evaluate(evidence, question)`

- **语义**: 执行双闸判定
- **错误**: 模型自评调用失败时按不通过处理，且原因记为「模型不可用」而非「证据不足」
- **不变量**: 结果中两道闸的结果分别可见；硬规则已判不通过时不再调用模型

#### `detect_conflict(answer, evidence)`（与 `ConflictJudge` 同文件，模块函数）

- **语义**: 判定答案与知识库是否冲突，并给出以知识库为准的答案
- **错误**: 判定失败时返回「按知识库作答」且不泄漏模型认知
- **不变量**: 判定结果含分歧主题、双方说法与出处引用

#### `EpisodicRecorder.record(event)`

- **语义**: 记录一次情景事件
- **错误**: 不抛异常，失败只写日志
- **不变量**: 事件含发生时刻与会话标识

#### `EpisodicRecorder.prune()`

- **语义**: 淘汰超出 5000 条上限或早于 180 天的情景事件
- **错误**: 清理失败只写日志，不影响记录
- **不变量**: 被淘汰的数量记入统计；淘汰过程不留原文副本

#### `ConsolidationEngine.approve(entity_id)`

- **语义**: 把一条待审的规律转为生效，使其可计入作答证据
- **错误**: 目标不存在或不是待审状态时返回错误
- **不变量**: 生效的规律仍带来源情景事件列表

#### `ConflictJudge.should_judge(answer, question)`

- **语义**: 用前置规则判断这次作答是否需要做冲突判定
- **错误**: 规则判定异常时按需要判定处理
- **不变量**: 命中具体断言或涉及制度、合同、金额时返回需要判定

#### `TermContext.lookup(term)`

- **语义**: 取出某个术语在知识库原文中的上下文片段及其位置
- **错误**: 查不到时返回空结果，不生成解释
- **不变量**: 返回的片段来自原文切片且带位置锚点

#### `ConsolidationEngine.consolidate(reason)`

- **语义**: 从情景事件归纳实体、规律与页面更新
- **错误**: 单条归纳失败跳过该条，不中断整轮
- **不变量**: 每条归纳结果带来源情景事件标识

## 4. 非功能性约束

### 4.1 性能

**基准机**：性能类指标一律在基准机上测得——i7-12700H（14 核 20 线程）+ RTX 3060 Laptop
6 GB + 16 GB 内存 + 本地 NVMe，嵌入模型 BAAI/bge-m3（fp16、单条截断 512 token），
解析主路径 PyMuPDF。基准机定义见 proposal 的 ASM-013。

**两层基准数据集**：绝对值指标在**真实工作域**上测——真实工作域是唯一能反映真实文档结构
复杂度的数据集，也是「每分钟多少个文件」这类数字唯一的证据来源。**合成基准集**由固定随机种子的
生成器按结构画像产出（可重建、不入库），只用于回归门：每次提交跑一遍，判据是相对上次
基线不退化 10%。合成文档的结构比真实文档简单（无复杂排版、无扫描件、无嵌入字体子集），
其吞吐数字偏乐观，因此不作为验收结论。

**建库类**

- 首次建库到可检索 SHALL 达到**每分钟 150 个文件**以上的速度（AC-P-001）；按此速度，
  一个 5000 个文件的工作域在 35 分钟以内可检索。**为什么是速度而不是总量**：
  「5000 个文件、20 GB、两小时」这种承诺需要一份没人有的语料，而且它换算出来的速率
  实现的版本也达不到——**承诺要能测，也要跟得上实现**。速度跟着工作域的大小走，
  在任何工作域上都能测、能比；真实工作域的结构画像随验收报告一起记录，
  数字因此是可以解释的
- 建库完成的判据是长尾层切片可检索；核心层页面在后台逐份产出，不阻塞建库完成（AC-F-026）
- 解析阶段 SHALL 达到 120 个文件每分钟以上的吞吐（AC-P-010）
- 嵌入阶段 SHALL 达到 15 个切片每秒以上的吞吐（AC-P-011）
- 索引落库阶段 SHALL 达到 500 个切片每秒以上的吞吐（AC-P-012）
- 核心层文档不超过 200 份时，长尾层索引 SHALL 达到每分钟 150 个文件以上的速度（AC-P-007）
- 核心层文档的编译 SHALL 在 5 分钟以内完成，不含模型排队等待（AC-P-008）

**问答类**

- 检索首批证据 SHALL 在 2 秒以内返回（AC-P-002）
- 首个生成令牌 SHALL 在 5 秒以内产出（AC-P-003）
- 拒答判定与冲突判定的合计耗时 SHALL 在 3 秒以内（AC-P-004；两项各是一次模型往返，
  预算按往返计——proposal §2.3 有说明）
- 桌面端冷启动到可提问 SHALL 在 8 秒以内（AC-P-005）
- 单文件重建索引 SHALL 在 60 秒以内可检索（AC-P-006）
- 核心层页面已有可用结论时，证据 SHALL 在 2 秒以内返回且不触发长尾层切片检索（AC-P-009）；
  **问题点名了文件时除外**——此时长尾层在那份文件里检索，范围更窄，仍然快（ADR-047）

**延迟怎么量**（口径写在这里，是为了每次测出同一个数；实测脚本 `scripts/bench/latency.py`）

- **首批证据（AC-P-002）**：从**检索开始**（定位候选文件）到**证据取出**为止——不含模型理解那一步，
  也不含答案生成。各步的起止时刻由 SSE 的 trace 事件给出，所以同一次回答里的几个数出自**同一次运行**
  （跨运行的数字能差 8%，那不是系统的问题）
- **首个 token（AC-P-003）**：从请求发出到第一个 `token` 事件到达，**含模型的网络往返**
- **判定合计（AC-P-004）**：闸门（硬规则 + 模型自评）的耗时 **加上** 冲突判定的耗时。
  两项**各是一次模型往返**（实测 1.13 秒 + 1.37 秒，本地部分只占几毫秒），
  所以预算是 3 秒——1.5 秒在云端模型下达不到
- **冷启动（AC-P-005）**：从进程起到 `/api/v1/health` 回答——桌面端等的就是这个
- **单文件重建（AC-P-006）**：从「重建这个文件」到「它的内容能被搜到」
- **核心层编译（AC-P-008）**：一份核心层文档从通读到页面产出
- **核心层证据（AC-P-009）**：核心层检索的耗时，外加「**长尾层没有被检索**」这个事实
  （检索器自己报 `longtail_searched`，不是靠猜）；**点名了文件的问题除外**——
  那时长尾层要搜，但搜的是**一个文件**（ADR-047）

### 4.2 安全

- **Key 管理**: 模型供应商的密钥只从环境变量读取，配置文件里只写环境变量名；桌面端侧的凭据库读写接口保留但默认不启用
- **数据安全**: 文档原文、索引、情景事件、编译页面与审计日志全部落在本地数据目录；发给模型供应商的内容限于当前提问与召回片段，且发前经脱敏
- **访问控制**: 后端只监听本机回环地址；出站仅限白名单域名；本机代理隧道被拦截

### 4.3 错误处理与优雅降级

- 模型调用失败 → 区分为「模型不可用」与「证据不足」两类，错误详情只进本地日志
- 冲突判定失败 → 仍按知识库作答，不把模型认知泄漏给用户
- 引用校验失败（编号越界或解析不出）→ 转拒答，不给出与结论无关的引用
- 全文通道不可用 → 降级为纯稠密；稠密通道不可用 → 整体失败，不静默返回空
- 重排模型不可用 → 按融合分顺序返回
- 脱敏规则异常 → 跳过该条规则，其余继续
- 单个文件摄取失败 → 记录失败原因并继续处理其余文件
- 文件超过体积上限（默认 100 MB）→ 跳过并在结果中说明上限，不把文件读进内存
- 工作域内没有可检索的文件 → 明确告知知识库是空的，并引导用户添加文件
- 文件内容被修改 → 保留已入库的旧版本，直到用户显式触发重建
- 不受支持的文件 → 在建库结果中列出该文件与原因，不静默跳过
- 分层判定失败 → 归为长尾层并记录原因，不阻断建库
- 核心层文档编译失败 → 标记该文件为「待重编译」，继续处理其余文件，提问时不检索该文件的内容
- 核心层页面与长尾层切片结论不一致 → 以核心层页面为准，在答案中标注两层不一致
- 页面结论缺出处锚点 → 该条结论不进入作答证据，转入拒答候选
- 冲突判定被前置规则跳过 → 视为未发现冲突，正常作答并记录跳过原因
- 规律处于待审状态 → 不计入作答证据，实体照常生效
- 术语在知识库中查不到上下文 → 显示未找到，不生成任何解释
- 索引写入部分失败 → 标记该文件为「待重建」，不留下半成品

### 4.4 可运维性

- **日志**: 本地日志文件，区分级别；启动信息经标准输出打印；错误响应不携带异常原文
- **健康检查**: 报告关系库、向量库、全文索引、模型网关 4 个组件的状态
- **配置热更新**: 模型路由与检索权重可在重启后生效；工作域与索引变更即时生效
- **落点**: 索引、日志、审计与模型缓存全部在一个可配置的本地根目录下（`YUANWORK_HOME`）；
  **启动时打印实际落点**（数据目录与模型缓存目录各一行），让人随时知道东西在哪；
  模型缓存目录在**进程最早期**写进 `HF_HOME`——huggingface_hub 的缓存位置是导入时算定的
  常量，晚一步设置不报错，只是静默不生效（ADR-045）

| 编号 | 假设 | 前提不成立时的退化方案 |
|------|------|------------------------|
| ASM-001 | 单人单工作域，不引入多用户与共享 | 若要支持多工作域，检索层需增加工作域过滤维度，索引按工作域分区 |
| ASM-002 | 现有实现作为资产复用，处置逐项列在 §6 | 若某模块的复用价值低于改造成本，按 §6 判为重做而不是改造 |
| ASM-003 | 数据与索引全部本地，只有提问与召回片段发给模型供应商 | 若供应商不可用，退化为本地模型，准确度下降但引用与拒答两条承诺不受影响 |
| ASM-004 | 语义记忆分两层，切片为底、实体图谱为上 | 若上层归纳不可靠，下层切片仍可独立支撑引用这条承诺 |
| ASM-005 | 情景记忆的来源限定为用户与知识库的交互 | 若需要跨应用的工作记忆，须重新评估隐私承诺，不在默认范围内 |
| ASM-006 | 本期一次性交付完整形态 | 若周期不足，优先保证引用与拒答两条承诺（tasks 的 M1 与 M2），wiki 与记忆工程顺延 |
| ASM-007 | wiki 页面由系统自动生成骨架，用户可编辑 | 若编辑标记的实现成本过高，先发布只读页面并禁止自动重编译覆盖 |
| ASM-008 | 证据充分性由两道闸判定，取更保守的一侧 | 若模型自评不可靠，退化为只用硬规则闸，宁可多拒答 |
| ASM-009 | 文档分两层：核心层写入时编译，长尾层查询时检索 | 若分层判定不准，核心资料会退化为切片检索，准确度下降但引用与拒答两条承诺不受影响 |
| ASM-010 | 编译页面的每条结论都带出处锚点 | 若锚点对齐无法保证，该结论降级为不可引用，不进入作答证据 |
| ASM-011 | 核心层文档的编译发生在摄入时，不在提问关键路径上 | 若无法在摄入时完成，退化为按需编译，延迟转移到提问路径 |
| ASM-012 | 使用者覆盖各行各业与各专业程度，普遍缺少自行判读资料与答案的专业能力，系统替他找、替他核，不替他判断 | 若证据充分性判定不可靠，宁可多拒答并给出位置，不做主动推断 |
| ASM-013 | 性能指标在基准机上测得：14 核 CPU + 6 GB NVIDIA 显卡 + 16 GB 内存 + NVMe，嵌入 fp16 截断 512 token，解析主路径为 C 库 | 若用户机器低于基准机，指标按同一比例放宽，并在验收报告中记录实测环境 |
| OQ-001 | 已拍板：用户编辑过的页面按段落级合并，重编译只替换模型生成的段落（ADR-037） | 若改为整页保护，用户未编辑的部分也不再更新 |
| OQ-002 | 已拍板：情景事件按 5000 条与 180 天双上限淘汰，淘汰时只计数（ADR-038） | 若容量上调，磁盘占用与隐私暴露期随之增长 |
| OQ-003 | 已拍板：实体自动生效，规律待审且未经确认不计入作答证据（ADR-039） | 若改为全部自动生效，错的规律会带偏回答 |
| OQ-004 | 已拍板：冲突判定用前置规则筛选，高风险场景强制判定（ADR-040） | 若改为每次都判定，延迟与调用成本回到每次问答 |
| OQ-005 | 已拍板：术语上下文取自原文，不生成术语解释（ADR-041） | 若改为模型生成解释，会引入无法核验的生成内容 |

| 检索：只查切片，无页面检索路径 | 核心层优先，结论足够则短路 | 改造 | 现状无分层检索编排（ADR-034） |
| 嵌入：CPU 版 torch，batch 8，fp32 | CUDA 版 torch，fp16，批量提交，截断 512 token | 改造 | 嵌入是建库耗时的大头（ADR-035） |
| 嵌入：CPU 上还在算没人读的稀疏通道，批硬编码成 8，切片乱序进批 | 关掉摄入侧的稀疏通道，批大小可配（32），按长度分桶，超时随批大小伸缩，int8 可选 | 改造 | 白算的活不必算；向量一个字节没变（ADR-042） |
| 解析：pdfplumber 纯 Python 逐页 | PyMuPDF 主路径，pdfplumber 兜底表格与复杂版式 | 改造 | 解析是纯 Python 的速度天花板（ADR-036） |
| 摄取：逐文件串行，多核闲置 | 多进程解析加批量嵌入，带限流与断点续跑 | 改造 | 串行让并发能力白白浪费（§1.1 `BatchIngestor`） |
| 页面编辑：没有编辑端点，页面无编辑标记 | 编辑端点加段落级归属，重编译按块合并 | 重做 | 现状用户改不了页面，编辑优先无从谈起（ADR-037） |
| 情景事件：无淘汰机制 | 按 5000 条与 180 天双上限清理并计数 | 改造 | 事件逐轮增长，含用户提问内容（ADR-038） |
| 归纳产出：实体与规律都不分状态 | 规律待审、实体自动生效 | 改造 | 现状无状态位，未审的推断会直接进答案（ADR-039） |
| 冲突判定：每次都调用，失败时返回「不相关」 | 前置规则筛选加高风险强制；判定失败按知识库作答 | 改造 | 现状失败语义会把模型原答案透出（ADR-040） |
| 术语：答案里就是一段文字 | 术语可点开看原文上下文 | 改造 | 现状普通人无从下手（ADR-041） |
| 落点：数据目录是相对路径（跟着 cwd 跑），模型缓存落在系统盘的 HuggingFace 默认目录里 | 一个可配置的根目录 `YUANWORK_HOME`，索引与模型缓存都在它下面，落点显式可查 | 改造 | 系统盘只剩 4.2 GB，本项目的模型缓存占了 4.70 GB；同一个项目会落到不同目录（ADR-045） |
| 切片：按字符切（2000 字符 ≈ 500 token —— 那是英文的换算），嵌入器按 512 token 读 | 切片长度用嵌入模型读得下的 token 量，两处同一个配置 | 改造 | 9.8% 的切片超限，10.6% 的内容模型没读到，而它在语义通道里比噪声还远（ADR-046） |
